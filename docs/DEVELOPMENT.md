# 开发记录

> 本文档记录 maimen-wrapped 的关键设计决策与技术权衡，供后续维护者参考。

## 项目背景

本项目为「麦当劳程序员节创意开发大赛」参赛作品，使用 WorkBuddy 完成构思、开发与调试。

赛事要点：

- 基于麦当劳 MCP Server 开发 Skill
- 排名规则：**按 GitHub Star 数**，Star > 0 即入榜
- 榜单窗口：2026-10-09 10:30 — 2026-10-25 23:59

## 核心设计决策

### 决策 1：形态选择「故事卡片流」而非「长页报告」

**背景**：赛事排名纯按 Star 数，分享转化率是决定性因素。

**权衡**：

| 方案 | 优点 | 缺点 |
| --- | --- | --- |
| 长页滚动报告 | 信息密度高，开发快 | 截图只能截局部，分享意愿低 |
| **故事卡片流（选定）** | 每张独立成图，截图即传播 | 开发复杂度略高 |

**结论**：采用 10 张 9:16 全屏卡片 + scroll-snap 翻阅。该形态经 Spotify Wrapped / 网易云年度报告验证，是分享转化率最高的模式。

### 决策 2：新增「麦门称号」系统

**背景**：单纯的数据罗列缺乏分享动机。

**设计**：规则引擎按数据发放个性化称号（深夜麦乐送战士 / 早餐狂魔 / 穷鬼套餐守护者等）。称号是用户晒图的**第一动机**——"你是什么称号"天然具备话题性。

**规则优先级**：夜宵占比 > 早餐占比 > 单品占比 > 外送占比 > 客单价 > 单数，兜底「稳健干饭人」。

### 决策 3：BGM 使用 Web Audio 原创合成

**背景**：用户最初希望使用麦当劳官方歌曲。

**合规分析**（已向用户说明并确认）：

- 官方歌曲涉词曲 + 录音双重版权，音频文件入公开仓库构成版权侵权风险
- 官方条款明确「不构成对麦当劳及其关联方商标的任何授权」、禁止暗示官方背书
- 参赛声明要求合规性承诺，使用官方歌曲有取消资格风险

**结论**：改用 Web Audio API 现场合成原创 jingle（C 大调五声音阶动机 + 三角波 + ADSR 包络，约 100 行 JS），零音频文件，反而成为技术卖点。

**附带处理**：浏览器自动播放策略要求用户手势，因此封面卡设计「开启你的麦门之旅」按钮，点击同时解锁音频与翻页，将限制转化为开场仪式。

### 决策 4：只读原则与自动降级

**只读原则**：仅调用查询类工具（`order-list`、`query-order`、`list-nutrition-foods`、`query-my-account`、`available-coupons`、`query-my-coupons`、`campaign-calendar`、`now-time-info`），绝不调用下单/取消/抽奖等写操作，确保对用户账号零副作用。

**自动降级**：不同账号数据完整度差异大，报告对缺失数据不编造，直接隐藏对应卡片并动态重排页码：

| 缺失数据 | 卡片数变化 | 处理 |
| --- | --- | --- |
| 完整数据 | 10 | 全部展示 |
| 无金额 + 无营养 | 8 | 跳过花费卡、热量卡 |
| 无下单时刻 | 9 | 跳过干饭时钟卡，称号降级为不含时段维度的规则 |

## 关键技术问题与修复

### 问题 1：mcp SDK 2.3.0 API 变更

**现象**：按 1.x 文档写的 `streamablehttp_client(url, headers=...)` 导入失败。

**根因**：安装到的 `mcp` 2.3.0 版本中：

- 函数更名为 `streamable_http_client`（下划线分隔）
- 不再接受 `headers` 参数，需通过 `create_mcp_http_client(headers=...)` 构造 `httpx2.AsyncClient` 注入
- 返回值为 `(read, write)` 二元组，而非三元组

**修复**：使用 `contextlib.AsyncExitStack` 管理 `httpClient` → `streamable_http_client` → `ClientSession` 三层生命周期。

**验证**：`from mcp.client.streamable_http import streamable_http_client` 导入成功，签名确认为 `(url, *, http_client=None, ...)`。

### 问题 2：无时刻数据被误判为时段偏好

**现象**：订单仅含日期（如 `2026-01-08`）时，「干饭时钟」卡片仍被渲染，所有订单被归入「早餐」时段（因解析后 hour=0）。极端情况下称号会误判为「早餐狂魔」。

**根因**：日期字符串解析后时刻默认为 `00:00:00`，聚合层无法区分「真实凌晨下单」与「数据无时刻」。

**修复**：

1. 在 `SOrder` 中新增 `bHasClock` 字段
2. 新增 `_parse_datetime_ex()`，在解析阶段判定时间精度（纯日期格式 / 无冒号的字符串 → `bHasClock=False`）
3. 聚合时仅在 `bHasClock` 为真时统计时段分布
4. 称号引擎在无时刻时跳过时段类规则（规则 1、2）
5. 渲染器与 `_make_insights` 同步加保护

**验证**：

| 场景 | 卡片数 | 称号 |
| --- | --- | --- |
| 完整数据 | 10 | 深夜麦乐送战士 |
| 无时刻 | 9 | 板烧鸡腿堡信徒（正确降级） |

### 问题 3：热量换算数值脱离直觉

**现象**：样例数据（127 单）渲染出「绕操场 4030 圈」「慢跑 1612 公里」，数字过大导致读者无感且显得荒谬。

**分析**：换算公式本身数学正确（单均 761 kcal，属正常范围），问题在呈现方式。

**修复**：改用更有冲击力的小数字换算——「≈ 190 个巨无霸」「≈ 201 小时慢跑消耗」，并标注「按 60kg 体重估算」。

## 测试覆盖

### 已验证场景

1. **端到端（完整数据）**：127 单 → 10 张卡片，营养匹配率 100%
2. **降级 A（无金额 + 无营养）**：→ 8 张卡片
3. **降级 B（无下单时刻）**：→ 9 张卡片，称号正确降级
4. **模块编译**：全部模块 `py_compile` 通过
5. **导入完整性**：6 个模块导入无错误

### 待验证场景（需真实 Token）

以下场景依赖真实账号数据，需申请 MCP Token 后验证：

- `order-list` 实际返回结构（是否含金额、下单时刻、就餐方式、分页参数）
- `query-order` 的金额口径（实付 / 原价 / 积分抵扣）
- `list-nutrition-foods` 的条数、字段名、能量单位（kJ vs kcal）
- 订单时间跨度的实际上限（影响「年度」文案准确性）
- 限流表现（多订单账号的并发补全）

**建议流程**：申请 Token 后先运行 `--probe` 模式，查看 `data/probe/SCHEMA_REPORT.md` 字段核对报告，再据此调整卡片取舍。
